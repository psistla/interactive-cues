Claude Operating Guide
Routing, orchestration, and drift control across surfaces

How Claude actually works

The model is not the product. The harness is. Understanding where the leverage sits changes what you build.

Verified against official docs · 10 Aug 2026 · Claude Code v2.1.2xx era · Max plan

The distinction that matters

Claude is a model. Claude Code is an agentic harness: the tools, context management, permission gating, memory loading, and the loop that chains actions together. Anthropic's own glossary draws this line explicitly. Nearly everything you can tune lives in the harness, not the model.

This is why "which model should I use" is usually the least interesting question in the room, and why a well-configured Sonnet session routinely beats a badly-configured Opus one.

The loop

Every task runs through three blended phases: gather context, take action, verify results, repeating until done. Each tool result feeds the next decision. You are inside the loop, not outside it: you can interrupt with Esc, or type a correction mid-turn without stopping the running tool.

Every extension point you will read about in section 02 plugs into a named phase of this loop. That is the whole mental model.

What actually makes it powerful

Four things, in descending order of how much they explain:

1. Verification, not generation

The step-change is not that Claude writes code. It is that Claude can run the test, read the failure, and patch. Anything you give it to check against (a test suite, a type check, a screenshot, an acceptance criterion, an exit code) compounds. Anything you do not is a coin flip. This is the single highest-leverage input you control, and it is upstream of every other tuning decision.

2. Context economics

The docs state the binding constraint plainly: the context window fills fast and performance degrades as it fills. Almost every best practice is downstream of that one fact. Compaction clears older tool outputs first, then summarises; detailed instructions from early in a conversation can be lost. A large CLAUDE.md is not free knowledge, it is a recurring per-request tax that also reduces adherence.

3. Isolation primitives

Subagents, forked skills, dynamic workflows, and agent teams all exist to let you spend context you do not have to hold. A subagent can read forty files and return three hundred tokens. A workflow can run hundreds of agents and land one report. Learning to route work into isolated context is the difference between a session that stays sharp and one that thrashes.

4. Determinism where it matters

An instruction is a request. A hook is a guarantee. CLAUDE.md content arrives as a user message after the system prompt, and Claude "tries to follow it, but there's no guarantee of strict compliance." A PreToolUse hook that blocks the edit is enforcement. Mature setups know which of their rules are requests and which are guarantees, and put each in the right layer.

What does not make it powerful

Falsifiable claims

Bigger CLAUDE.md does not help. Falsifier: run /doctor on a repo with a 400-line CLAUDE.md. It proposes trims and cuts content Claude can derive from the codebase.

More installed skills does not help. Falsifier: the skill listing has a context budget of 1% of the model's window. Past it, descriptions are truncated starting with the skills you invoke least, which silently strips the trigger keywords. /doctor reports the listing cost.

Prompt cleverness is not the frontier. Falsifier: compare an elaborate prompt with no verification target against a plain prompt plus "run the tests after." The second wins consistently.

Reframe worth holding

You did not ask a knowledge question, you asked a routing question. Feature knowledge is now a commodity with a shelf life of weeks. The durable skill is: for this task, which surface, which primitive, and what is the cheapest artifact that makes that choice repeatable next time? Sections 02 through 04 are the routing procedure. Section 08 is the perishable part and is dated accordingly.

The four confusions worth settling

CLAUDE.md vs Skill

CLAUDE.md loads every session and cannot trigger a workflow. A skill loads on demand and can be invoked as /name. Rule of thumb from the docs: keep CLAUDE.md under 200 lines; if it is growing, the overflow is either a rule or a skill.

Rules vs Skill

Rules load every session, or whenever a matching file is opened (paths: frontmatter). Skills load only when invoked or judged relevant. Rules are for "always true for these files." Skills are for "sometimes needed."

Skill vs Subagent

A skill is content loaded into a context. A subagent is a separate context. They compose: a skill with context: fork runs itself in a subagent; a subagent with a skills: field preloads skills at launch.

Hook vs Skill

A hook always fires on its event and costs zero context unless it returns output. A skill is interpreted and can vary. "Never edit .env" in CLAUDE.md is a request. A PreToolUse hook is enforcement.

Non-obvious

Because CLAUDE.md is additive rather than overriding, two files that contradict each other do not resolve deterministically. The docs say Claude "may pick one arbitrarily." In a monorepo, use claudeMdExcludes in .claude/settings.local.json to drop other teams' files.

The growth path

Do not configure everything up front. Each primitive has a trigger:

  1. Claude gets a convention wrong twice → add it to CLAUDE.md
  2. You type the same prompt to start a task → save it as a user-invocable skill
  3. You paste the same playbook a third time → capture it as a skill
  4. You keep copying from a tab Claude cannot see → connect it as an MCP server
  5. A side task floods your window → route it through a subagent
  6. Something must happen every time → write a hook
  7. A second repository needs the same setup → package it as a plugin

On "graphs"

Correction to a common assumption

There is no declarative graph primitive in Claude Code. No YAML DAG, no node-and-edge config. The closest thing is a dynamic workflow: plain JavaScript with top-level await, where agent() spawns one subagent and pipeline() maps one per item. Fan-out, branching, and joins are expressed as ordinary control flow. If you are carrying a LangGraph-style mental model, drop it. The graph is the script.

export const meta = {
  name: 'audit-routes',
  description: 'Audit every route handler for missing auth checks',
}

const found = await agent('List every .ts file under src/routes/.', {
  schema: { type: 'object', required: ['files'],
    properties: { files: { type: 'array', items: { type: 'string' } } } },
})

const audits = await pipeline(found.files, file =>
  agent(`Audit ${file} for missing authentication checks.`, { label: file }),
)

return audits.filter(Boolean)

Workflow mechanics worth knowing before you spend on one

  • Trigger with the keyword ultracode in a prompt you type yourself, or plain language ("use a workflow"). It does not trigger from -p, scheduled tasks, webhooks, or PR comments, by design.
  • /effort ultracode makes Claude plan a workflow for every substantive task in the session. Session-scoped, resets on new session. Costly.
  • Hard caps: 16 concurrent agents, 1,000 agents per run. No filesystem or shell access from the script itself. No import().
  • Size guideline in /config: small (<5), medium (<15, the default), large (<50), unrestricted.
  • Watch and control with /workflows. Press s to save a run's script as a reusable /command.
  • Resume is order-sensitive. Cached results stop at the first agent that did not finish; every agent that started after it re-runs even if it completed. Many small agents preserve more progress than few long ones.
  • Workflow subagents always run in acceptEdits mode regardless of your session mode. File edits are auto-approved. Allowlist the shell commands they need before a long run.
  • /deep-research is the bundled workflow: fans out searches, cross-checks sources, votes on claims, filters out what did not survive.

Keeping a session running: three mechanisms

ApproachNext turn starts whenStops when
/goal <condition>The previous turn finishesA separate evaluator model confirms the condition holds
/loopA time interval elapsesYou stop it, or Claude judges the work done
Stop hookThe previous turn finishesYour own script or prompt decides

/goal, and how to write a condition that actually holds

/goal is a session-scoped wrapper around a prompt-based Stop hook. After each turn, a small fast model reads the condition plus the conversation and answers yes or no with a reason. On "no", the reason becomes guidance for the next turn.

The failure mode

The evaluator does not run commands or read files. It only judges what Claude has already surfaced in the transcript. A condition like "the code is correct" is unevaluable. "npm test exits 0 and the output is in this conversation" is evaluable. Write the check, not the wish.

A durable condition has three parts: one measurable end state, a stated proof method, and the constraints that must not be violated on the way there. Add a bound such as "or stop after 20 turns." Max 4,000 characters.

/goal does not change permissions. Pair it with auto mode for unattended runs: auto mode removes per-tool prompts, /goal removes per-turn prompts. They are complementary.

Parallelism and the surrounding machinery

Agent teams experimental

Independent sessions, shared task list, peer-to-peer messages. Higher token cost since each teammate is a separate Claude instance. Best for competing hypotheses and parallel review. Disabled by default.

Agent view

claude agents opens a monitor over background sessions: state, PR status, peek and reply, attach. Dispatch new agents from the view or from your shell. Worktree-isolated file edits.

Cross-session messaging

Sessions message each other directly without forming a team. Works across machines with approval gating. Useful when two long-running sessions need to hand off.

Worktrees

The isolation substrate. Parallel sessions on separate branches, subagents in their own checkouts, no edit conflicts. Clean up .claude/worktrees/ periodically.

Routines cloud

Scheduled, API-triggered, or GitHub-triggered runs in cloud environments. Each run is a fresh remote session, so it does not see ~/.claude/skills/. See section 04.

Scheduled tasks local

Desktop scheduled tasks run locally and do load your local skills. Seven-day expiry, jitter applied. Different animal from routines.

The two facts that cause the most confusion

1. Cowork and cloud sessions do not read ~/.claude/skills/ on your machine. They load the skills enabled for your claude.ai account, synced at session start. If a skill exists only locally, a routine invoking it reports "skill not found." Desktop scheduled tasks are the exception: they run locally and behave like any local session.

2. Plugin hooks and subagents run only in Cowork. In chat they appear greyed out. A plugin whose value is its hooks does nothing for you in a chat window.

The frontmatter portability trap

Claude Code accepts around twenty frontmatter fields. The Agent Skills open standard, which governs claude.ai uploads and the Skills API, accepts six:

name  description  license  compatibility  metadata  allowed-tools

Anything else is a hard error on upload, not a silently ignored field:

Unexpected key(s) in SKILL.md frontmatter: argument-hint.
Allowed properties are: allowed-tools, compatibility, description,
license, metadata, name

Claude Code-only body features also stop working: dynamic context injection (!`command`), $ARGUMENTS substitution, context: fork. A skill you want in every surface must be authored to the six-field spec, with the body carrying no shell injection.

Practical consequence

You need two authoring tiers, not one. Tier A skills are spec-compliant and portable everywhere. Tier B skills use the full Claude Code feature set and stay local. Deciding which tier a skill belongs to at authoring time is cheaper than discovering it at upload.

Drift control

You asked to treat behavioural, configuration, and quality drift as one problem. They are not one problem, but they share one solution shape: move each rule to the lowest layer that can enforce it.

The enforcement ladder

Determinism increases as you descend. Cost and rigidity increase too. Most people leave everything at rung 1 and then wonder why adherence is inconsistent.

  1. Conversation — zero persistence. Lost at compaction. Never put a standing rule here.
  2. Profile preferences / output style — persists across sessions on that surface. Still interpreted.
  3. CLAUDE.md — every session, additive, interpreted. Project-root CLAUDE.md survives compaction and is re-injected. Nested files and path-scoped rules are not.
  4. .claude/rules/ with paths: — loads only when relevant files are touched. Same enforcement strength, better context economy.
  5. Skill — full content on invocation, persists in context for the session. Re-invoke after compaction to restore.
  6. Hook — fires on its event, always. Zero interpretation. This is where a rule becomes a guarantee.
  7. Managed settings / permission deny rules — client-enforced regardless of what Claude decides. The floor.

Behavioural drift

Symptom: Claude honours your voice and format rules early, then stops.

CauseFix

The highest-value single change

Your absolute constraint (never name the employer) is currently a request at rung 2 or 3. It should be a PreToolUse deny hook on Write and Edit plus a Stop hook on output. That is the difference between "usually holds" and "cannot fail." Pattern in section 07.

Configuration drift

Symptom: behaviour differs between machines, repos, or surfaces, and you cannot say why.

  • Root cause is almost always copies. A skill in ~/.claude/skills/, a near-copy in a repo, and an upload on the account are three files that will diverge.
  • The fix is packaging. A plugin is the only construct that bundles skills, hooks, subagents, MCP servers, LSP servers, and default settings into one versioned, installable unit with a marketplace behind it. Everything else is manual synchronisation.
  • Symlinks for the rest. .claude/rules/ resolves symlinks and detects cycles, so one shared rules directory can serve every repo. Skill directories can be symlinks too, and a target reachable from two locations loads once.
  • Version and date the inventory. Drift you can see is a maintenance task. Drift you cannot see is a mystery.
Cache side effect worth knowing

Enabling or disabling a plugin, connecting or disconnecting an MCP server, switching models, or changing effort level all invalidate the prompt cache. Editing CLAUDE.md mid-session, invoking skills, and rewinding do not. Do your configuration churn at session boundaries, not mid-task.

Quality drift

Symptom: output degrades as the session runs long. This is the expected behaviour of a filling context window, not a malfunction.

  • Budget before you optimise. Run /context. If CLAUDE.md plus rules plus skill listing exceeds roughly 15% of the window at session start, you have a structural problem, not a prompting problem.
  • The kitchen-sink session is the named antipattern. One task, then an unrelated one, then back. Use /clear, a fork, or a second worktree instead.
  • Route volume into isolation. Anything that reads many files and returns a verdict belongs in a subagent or a forked skill, not the main window.
  • Trim the listing. skillOverrides with "name-only" frees budget without editing files you do not own. disable-model-invocation: true takes a skill to zero context cost until you invoke it.
  • Guide compaction. Add a "Compact Instructions" section to CLAUDE.md, or run /compact focus on the deployment change.
  • @path imports do not save context. Imported files load at launch just the same. Path-scoped rules are what actually reduce load.

P0 The constraint hook stack

Your non-negotiables become enforcement rather than requests. Three hooks, roughly forty lines total.

A. PreToolUse on Write and Edit — reject any payload containing the employer string. Exit code 2 blocks the call and returns the reason to Claude.

B. Stop, prompt-based — a model-evaluated check on the finished turn: employer name absent, no em dashes, load-bearing claims carry confidence and a falsifier, no generic closer. Returns block plus reason if any fail.

C. SessionStart — inject the current date, active project, and a one-line restatement of the format contract, so it is present in the window rather than assumed.

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{ "type": "command",
        "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/constraint-guard.sh" }]
    }],
    "Stop": [{
      "hooks": [{ "type": "prompt",
        "prompt": "Check the final assistant message. Fail if it contains an em dash, names an employer, opens with a filler phrase, or closes generically. Return {block, reason}." }]
    }]
  }
}

Success test: deliberately ask for a deliverable that names the employer. The hook blocks it. If it does not, the hook is not registered; check /hooks.

P1 CLAUDE.md diet plus path-scoped rules

Per repo: cut CLAUDE.md to under 200 lines of facts that apply everywhere. Move the rest into .claude/rules/ with paths: frontmatter so it loads only when relevant. In a Python CLI repo, deployment conventions should not be in context while you are editing tests.

P1 Goal-bounded verification loops

For CLI and pipeline work, stop babysitting turn by turn. Set an evaluable condition, pair with auto mode, walk away.

/goal `pytest -q` exits 0 with zero failures on Python 3.11 and 3.12,
`ruff check .` is clean, no file outside src/ or tests/ is modified,
and the full command output appears in this conversation. Stop after 15 turns.

Note the last clause: the evaluator only reads the transcript, so the condition must require Claude to surface the proof.

Success test: the goal clears on its own with an achieved entry in the transcript, rather than you clearing it manually.

P1 Adversarial review workflow for consequential deliverables

This is the pattern your evidence discipline has been asking for, and it is only cleanly available as a workflow: independent agents that review each other's findings before anything is reported, so a single confident pass cannot slip through.

P1 A small, named subagent set

Three is enough. More than five and you are building an org chart, not a toolkit.

  • evidence-auditor — reads a draft and tags every load-bearing claim as fact, inference, or speculation, flags the weakest assumption. Preload the evidence-discipline skill. Read-only tools.
  • architecture-reviewer — takes a design and returns the objections a sceptical principal would raise. Model opus, effort high.
  • deliverable-qa — checks a generated artifact against the design-system and constraint rules before it leaves the machine.

Success test: your main context stays under half full through a full deliverable cycle, because the reading happened elsewhere.

P2 Code intelligence and the right scheduling surface

Install the LSP plugins for your stack (pyright-lsp, typescript-lsp) from the official marketplace. They enable the LSP tool, which replaces broad file reads with symbol lookups, so net context use goes down. The binary must be on your PATH; the plugin does not install it.

For recurring work, route deliberately: cloud routines for repo-scoped checks with skills committed to the repo, desktop scheduled tasks for anything that needs local files or local skills. Choosing the wrong one produces a silent "skill not found."

Two traps

context: fork on a reference-only skill produces nothing: the subagent gets the knowledge but no task. Only fork skills with explicit step-by-step instructions.

An invoked skill's content stays in context for the whole session. Every line is a recurring cost. Keep SKILL.md under 500 lines and push detail into sibling files.
