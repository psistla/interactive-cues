Reference Architecture

Dynamic Agentic RAG for a Research Analyst Product

An open source blueprint for a system that ingests an evolving document corpus, retrieves inside a reasoning loop, produces cited analyst output, and proves its own quality with a measurable evaluation gate.

Open source stack Postgres + pgvector LangGraph Docling Eval-gated

What this product actually is

A research analyst product is not a chatbot with documents attached. It is a system that produces defensible written analysis over a corpus that keeps changing, where every claim traces back to a source passage and a document version.

Three capabilities separate it from ordinary retrieval augmented generation. Each one drives a distinct architectural requirement, and skipping any of them produces a demo rather than a product.

Capability 01

Multi-hop synthesis

Answers require combining evidence from several documents, not locating one passage. Retrieval must sit inside the reasoning loop so the system can retrieve again after reading.

Capability 02

Provenance at claim level

Every sentence of output carries a citation to document, version, page, and passage. An analyst who cannot verify a claim will not use the tool twice.

Capability 03

Change awareness

New documents change previous conclusions. The system re-runs standing questions against the updated corpus and reports what moved and why.

The defining design decision

Change awareness is what makes the system dynamic in a way a user can feel. Automatic indexing alone is invisible: the corpus grows and nothing observable happens. Standing questions turn ingestion into a product surface, because every new document produces a diff against previously answered questions. Build this in phase 3, not as a phase 7 nicety.

System layers

SourceObject storage or watched directory holding raw PDFs and other source formats. Immutable, append only, the system of record.
IngestionEvent driven workers: detect, hash, parse, structure, chunk, enrich, embed, upsert. Idempotent and resumable.
Knowledge storePostgres holding documents, versions, chunks, embeddings, extracted claims, and entities. One database, several tables.
RetrievalHybrid dense and lexical search fused with reciprocal rank fusion, followed by cross encoder reranking, with mandatory metadata filters.
AgentStateful graph: plan, retrieve, read, verify, synthesize. Budgeted, checkpointed, fully traced.
ExperienceStreaming answers, inline citations, source viewer with passage highlight, evidence panel, ingestion console.
QualityGolden question set, retrieval and generation metrics, CI gate, production trace sampling, drift monitor.

Non-negotiable behaviours

Refuse rather than guess

Below a retrieval score floor the system states that the corpus does not cover the question and offers the nearest material. Refusal quality is a measured metric, not an accident.

Currency by default

Retrieval filters to current document versions unless the user explicitly asks for history. Superseded content stays indexed but is unreachable by default.

Extractive bias

The generator quotes and attributes rather than paraphrasing freely. Low temperature, strict grounding prompt, post-hoc citation verification.

Bounded work

Every agent run carries a hop ceiling, a token ceiling, and a wall clock ceiling. Unbounded agents are how cost incidents happen.

Data model

-- One row per logical document, many rows per revision
CREATE TABLE documents (
  doc_id        uuid PRIMARY KEY,
  source_uri    text NOT NULL,
  content_hash  char(64) NOT NULL,          -- SHA-256 of raw bytes
  title         text,
  category      text,                        -- your corpus taxonomy
  version_label text,
  published_at  date,
  valid_from    date,
  valid_to      date,                        -- NULL = current
  supersedes    uuid REFERENCES documents(doc_id),
  access_tier   text NOT NULL DEFAULT 'internal',
  parse_status  text NOT NULL DEFAULT 'pending',
  parse_conf    real,
  page_count    int,
  ingested_at   timestamptz DEFAULT now(),
  UNIQUE (content_hash)
);

CREATE TABLE chunks (
  chunk_id      uuid PRIMARY KEY,
  doc_id        uuid NOT NULL REFERENCES documents(doc_id) ON DELETE CASCADE,
  chunk_ord     int  NOT NULL,
  section_path  text[],                      -- ['3','3.2','Capital adequacy']
  page_from     int,
  page_to       int,
  bbox          jsonb,                       -- enables highlight-on-citation
  content       text NOT NULL,             -- verbatim passage
  context_head  text,                        -- generated situating sentence
  token_count   int,
  embedding     vector(1024),
  embed_model   text NOT NULL,             -- pinned for reindex safety
  tsv           tsvector GENERATED ALWAYS AS
                (to_tsvector('english', content)) STORED,
  UNIQUE (doc_id, chunk_ord)
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks USING gin (tsv);
CREATE INDEX ON documents (category, valid_to, access_tier);

-- Analyst-grade addition: extracted, attributable assertions
CREATE TABLE claims (
  claim_id    uuid PRIMARY KEY,
  chunk_id    uuid REFERENCES chunks(chunk_id) ON DELETE CASCADE,
  subject     text, predicate text, object text,
  as_of       date,
  confidence  real,
  embedding   vector(1024)               -- contradiction detection
);

Chunking policy

  • Split on structure, not characters. Use the heading tree the parser recovered. A chunk that spans two sections is a chunk that retrieves badly and cites confusingly.
  • Target 500 to 900 tokens with roughly 15 percent overlap at section boundaries only.
  • Never split a table. Keep it whole and store it as Markdown. If it exceeds the ceiling, chunk by row groups with the header repeated.
  • Prepend a context header. One or two generated sentences naming the document, section, and date. This measurably improves retrieval on pronoun-heavy and abbreviation-heavy passages, at the cost of a one-time generation pass during ingestion.
  • Carry bounding boxes. Without them the highlight-on-citation interaction is impossible to build later, and that interaction is the product's signature.
The reindex problem, planned for on day one

You will change embedding models. When you do, every vector in the store is invalid, and the corpus is unavailable if you reindex in place. Pin embed_model on every chunk row, build the new index in a shadow table, run the golden set against both, then cut over with a single transaction. Budget this as a recurring operation, roughly annual, not as a one-off migration.

Retrieval

Retrieval quality sets the ceiling on everything downstream. A better model cannot rescue evidence that was never retrieved, and the cheapest quality gains in the entire system live in this layer.

The pipeline

01FilterCurrency, tier, category
02DenseVector top 50
03LexicalBM25 top 50
04FuseReciprocal rank fusion
05RerankCross encoder top 8
06ExpandNeighbour chunks

Why each stage exists

StageFailure it fixesTypical cost
Metadata pre-filterCiting a superseded revision, or content the user may not seeNegligible, index-backed
Dense vector searchVocabulary mismatch between question and documentLow, HNSW
Lexical BM25Exact identifiers, clause numbers, product names, rare termsLow, GIN index

Highest return per hour of work

Hybrid retrieval plus a reranker resolves the majority of retrieval failures in a naive system. Do this before graph retrieval, before fine tuning, and before adopting a larger generation model. Measure the delta on the golden set so you can prove it rather than assert it.

Fusion and filtering, concretely

async def retrieve(q: str, flt: Filters, k: int = 8) -> list[Chunk]:
    # 1. Mandatory filters. Applied in SQL, never after generation.
    where = build_predicate(
        current_only = flt.as_of is None,     # valid_to IS NULL
        tiers        = flt.user_tiers,            # entitlement
        categories   = flt.categories,
    )

    # 2. Two independent recall paths, deliberately over-fetched.
    dense, lexical = await asyncio.gather(
        vector_search(embed(q), where, limit=50),
        bm25_search(q, where, limit=50),
    )

    # 3. RRF: rank-based, so the two score scales never need calibrating.
    fused = rrf(dense, lexical, k_const=60)

    # 4. Precision pass. This is where relevance is actually won.
    scored = await cross_encode(q, fused[:50])
    top    = [c for c in scored if c.score >= FLOOR][:k]

    # 5. Honest emptiness beats a confident wrong answer.
    if not top:
        raise InsufficientEvidence(nearest=scored[:3])

    return expand_neighbours(top)

Query transformation, used sparingly

Decomposition use

Split a compound analyst question into independent sub-questions and retrieve for each. This is the single highest value transformation for multi-hop work.

Rewrite on failure use

When the reranker returns nothing above the floor, rewrite once with corpus vocabulary and retry. Cap at one retry per sub-question.

Hypothetical document embedding measure first

Generate a fake answer and embed that. Helps on vague questions, adds a generation round trip, and sometimes hurts on precise ones. Only keep it if the golden set says so.

Graph retrieval defer

Entity graphs earn their operational cost only on connect-the-dots questions that hybrid retrieval demonstrably fails. Let the eval data justify it, not enthusiasm.

Contradiction detection

An analyst product gains disproportionate credibility from noticing that two sources disagree. The mechanism is cheap once claims are extracted at ingestion: cluster claim embeddings by subject and predicate, flag clusters whose objects diverge, and surface the disagreement with both citations rather than silently picking one. Do not attempt to adjudicate. Present both, dated.

The agent loop

Agentic means retrieval happens inside the reasoning loop rather than in front of it. The agent decides what to look for next based on what it has already read, and it stops when the evidence is sufficient or the budget is spent.

Graph topology

NodeResponsibilityExit condition
planDecompose the question into sub-questions with a stated evidence requirement for eachPlan produced, or question judged out of scope
retrieveRun the hybrid pipeline for the active sub-questionEvidence above floor, or one rewrite attempted
readExtract only passages that bear on the sub-question; discard the restSub-question marked answered, partial, or unsupported
reflectDecide: enough evidence, retrieve again, or new sub-questionHop budget or sufficiency reached
verifyCheck each drafted claim against its cited passage; strip unsupported onesAll claims supported or removed
synthesizeCompose the report with inline citations and an explicit gaps sectionOutput emitted

State flows through a single shared object. Nodes never call one another directly; they read and write state, and the runtime routes on conditional edges. This is what makes runs replayable from any checkpoint, which is what makes debugging possible.

class AnalystState(TypedDict):
    question:      str
    filters:       Filters
    sub_questions: list[SubQ]          # plan output, mutated as it runs
    evidence:      list[Evidence]      # chunk + why it was kept
    findings:      list[Finding]       # claim + supporting evidence ids
    gaps:          list[str]           # what the corpus could not answer
    hops_used:     int
    tokens_used:   int
    trace_id:      str

def route_after_reflect(s: AnalystState) -> str:
    if s["hops_used"] >= MAX_HOPS:        return "verify"
    if s["tokens_used"] >= MAX_TOKENS:    return "verify"
    if all_answered(s["sub_questions"]):  return "verify"
    return "retrieve"

graph.add_conditional_edges("reflect", route_after_reflect)

Budgets, which are not optional

8
Max hops

Runs that need more than eight retrieval rounds are almost always looping on a question the corpus cannot answer.

120k
Token ceiling per run

Enforced in state, checked at every routing decision, not left to the model's discretion.

240s
Wall clock ceiling

On expiry the agent emits partial findings with an explicit incompleteness notice rather than nothing.

The verification pass

Verification is the step that separates a research product from an autocomplete with footnotes. After drafting, each claim is checked independently against the passage it cites, by a separate call with only that claim and that passage in context. Claims that fail are removed, not softened. The removed claims become entries in the gaps section, which is itself valuable output: it tells the analyst where the corpus is silent.

The failure mode that kills trust

A citation that exists but does not support the sentence attached to it. Users spot-check the first two citations, find them plausible, then stop checking. If citation accuracy is 85 percent, the product is worse than no product, because it launders unverified claims through the appearance of rigour. Measure citation accuracy explicitly and gate releases on it.

Memory, in three narrow forms

  • Run memory. The state object within a single investigation. Nothing persists after.
  • Standing questions. Persisted questions replayed on corpus change, with stored prior answers for diffing. This powers Monitor mode.
  • Corpus notes. Durable observations about the corpus itself, such as which categories are thin or which documents are internally inconsistent. Written by the system, read by the planner.

Resist a general purpose long-term user memory in v1. It introduces non-determinism into evaluation, and you will not be able to tell whether a regression came from a code change or from accumulated state.

Deployment topology

Service 01

API

FastAPI, stateless, horizontally scalable. Holds no agent state; everything lives in Postgres checkpoints.

Service 02

Ingest workers

CPU heavy, bursty. Scale to zero between corpus updates. GPU pool only if using a GPU parser.

Service 03

Embedding and rerank

Separate service so the model can be swapped and versioned independently of application code.

Service 04

Postgres

Managed. Vectors, text, metadata, job state, agent checkpoints. Point-in-time recovery enabled.

Service 05

Redis

Queue broker plus retrieval cache. Cache keys include the filter set or you will serve cross-tenant results.

Service 06

Langfuse

Self-hosted trace and eval store. Also the substrate for the quality dashboard you show stakeholders.

What makes the frontend visually persuasive

In this product category, aesthetic quality and epistemic quality are the same thing rendered two ways. Beauty here means making the system's reasoning inspectable. Five interactions carry almost all of the perceived quality.

Streamed answer with citation chips appearing inlineThe system is working, and each claim is anchoredSSE streaming, citation ids emitted with text

Coupling worth noticing early

Every one of those five interactions depends on a decision made in the ingestion layer, weeks before any UI exists. Choose a parser that discards coordinates and the signature interaction becomes unbuildable without reprocessing the entire corpus. Frontend ambition is an ingestion requirement.

Interface principles

  • Answer first, apparatus second. Evidence, trace, and filters are progressive disclosure, not the default view.
  • Show uncertainty as structure. A gaps section and a contradiction flag are more convincing than a confidence percentage nobody can interpret.
  • Never spin without information. During a long investigation, stream the plan and each sub-question as it resolves. Perceived latency collapses.
  • Refusals get the same visual weight as answers. A well-designed "not covered" screen that lists the nearest material is a feature, and it teaches users where the corpus edges are.
  • Restraint over decoration. Dense information, strict hierarchy, one accent colour, no gratuitous motion. Analyst tools earn trust by looking calm.

Evaluation

Without a golden set you cannot tell whether a change helped. You will then tune on impressions for months and slowly get worse while feeling productive. This is the most commonly skipped component and the one that most determines whether the project succeeds.

Building the golden set

  1. Write 100 to 150 questions spanning the corpus categories. Draw them from real analyst questions where possible.
  2. For each, record the correct answer and the specific passages that support it. The passages matter more than the answer.
  3. Include roughly 15 percent unanswerable questions. These measure refusal, which nothing else does.
  4. Include roughly 20 percent multi-hop questions requiring at least three documents.
  5. Include questions whose answer changed between document versions. These test currency filtering.
  6. Version the set alongside the corpus. A golden set that drifts from its corpus is worse than none.

Recall sits first deliberately. If the passage never entered the candidate pool, no amount of reranking, prompting, or model upgrading can recover it, and every other metric is measuring the wrong thing.

The quality loop

Golden set runs in CI and blocks merges on regression. Production traces are sampled and scored reference-free, then reviewed weekly. Failures found in production become new golden set entries. The set grows to reflect real usage, and the system's quality becomes a number you can show a stakeholder rather than a claim you defend in a meeting.

Build plan

Nine phases, each with an exit gate. The gates matter more than the phases: they prevent the standard failure of building the agent before knowing whether retrieval works.

00Corpus reconnaissance2 to 3 days

Sample 50 documents covering the worst cases. Determine how many are scanned, how table-heavy they are, whether versions and effective dates exist, and whether the categories are meaningful or arbitrary. Parse them and read the output yourself.

Exit gateParsed Markdown is faithful on 45 of 50 documents, including tables. If not, fix parsing before writing any other code.
01Golden set first3 to 4 days

Write the questions and record supporting passages before building retrieval. This is counterintuitive and it is the highest leverage sequencing decision in the plan, because it forces you to discover what the corpus can and cannot support while changing course is still cheap.

Exit gate100+ questions with recorded supporting passages, including unanswerable and multi-hop cases.
02Ingestion pipeline1 to 2 weeks

Content-addressed detection, queue, parse, section-aware chunking, enrichment, embedding, idempotent upsert. Postgres schema with versions, tiers, and bounding boxes. Dead letter queue and reconciliation job.

Exit gateDrop a file into source storage; it is queryable within five minutes. Drop the same file again; nothing duplicates. Kill a worker mid-run; processing resumes.
03Retrieval core, no agent1 week

Hybrid search with fusion, mandatory filters, cross encoder reranking, neighbour expansion. Query it from a script. Measure every configuration against the golden set and record the results in a table you keep.

Exit gateRecall@20 at or above 0.90 and nDCG@8 at or above 0.75. Do not proceed on a lower number by promising to fix it later.
04Grounded generation and refusal4 to 5 days

Single-hop answers with inline citations, a score floor that triggers refusal, and the independent verification pass that strips unsupported claims.

Exit gateCitation accuracy at or above 0.95 on a hand-audited sample of 50 answers. Refusal correct on the unanswerable subset.
05Agent loop1 to 2 weeks

Planner, retrieve, read, reflect, verify, synthesize as a checkpointed graph. Hard budgets on hops, tokens, and wall clock. Full tracing from the first commit, not retrofitted.

Exit gateMulti-hop subset accuracy exceeds the single-hop baseline by a measurable margin. If it does not, the agent is adding cost and latency for nothing.
06Monitor mode4 to 5 days

Standing questions replayed when the corpus changes, with stored prior answers and a diff. This is where automatic indexing stops being invisible plumbing and becomes the product's most distinctive feature.

Exit gateAdding a document that changes a known answer produces a correct change digest without manual intervention.
07Interface2 weeks

Streaming answers, citation chips, PDF viewer with passage highlight, evidence panel, reasoning timeline, ingestion console. Build the highlight interaction first; it is the one that changes how people perceive the whole system.

Exit gateA user who has never seen the system verifies a claim back to its source page without instruction.
08Production hardening1 to 2 weeks

Authentication and entitlement filters, rate limits, per-tenant spend caps, golden set in CI, production trace sampling, staleness and reconciliation alerts, documented reindex runbook, backup and recovery test.

Exit gateAn embedding model swap can be executed end to end in a rehearsal without downtime or quality regression.

The plan in one paragraph

Sample the corpus and fix parsing before anything else. Write the golden questions before writing retrieval. Build ingestion as an idempotent, content-addressed pipeline that carries version, entitlement, and coordinate metadata on every chunk. Build hybrid retrieval with a reranker and measure it until recall clears 0.90. Add grounded generation with citations, a refusal floor, and an independent verification pass. Only then add the agent loop, with hard budgets and full tracing. Add standing questions so new documents visibly change conclusions. Build the interface around verifiability, with citation click-through to a highlighted source page. Harden last: entitlements, spend caps, evaluation in CI, and a rehearsed reindex path.
