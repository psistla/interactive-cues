Open table formats: what they are, what they fix, which one to pick

A data lake is a pile of files. A table format is the contract that turns the pile into a database table you can trust: one that has a schema, a history, and safe concurrent writes. Two formats matter in enterprise estates today, Delta Lake and Apache Iceberg, and the choice between them is simpler than the debate suggests.

1. What they are

Metadata on top of Parquet files.

2. What they fix

What they are

Parquet files plus a metadata layer that makes them behave like a table

CatalogTurns a name into a table. Holds permissions and the pointer to the current version.
Table metadataSchema, partitioning, version history: which files are part of the table right now.
Statistics and deletesMin, max and null counts per file for skipping; markers for deleted rows so files are not rewritten.
Data filesParquet. Immutable, portable, readable by any engine. Identical in both formats.

The one difference that explains the rest

Delta Lake keeps its truth in a transaction log inside the table folder. A catalog is helpful but optional. Grew up inside Databricks and Microsoft Fabric.

Apache Iceberg keeps its truth in the catalog, which points to the current metadata file. No catalog, no table. Grew up at Netflix for many engines sharing one lake; native to Snowflake, AWS and Google.

By 2026 both support the same core features: row-level deletes without rewrites, time travel, schema evolution, change tracking, semi-structured columns. The differences that remain are about ecosystem, not capability.

What they fix

Six problems every file-based lake hits, and how a table format solves each

WithoutA job fails halfway and readers see half-written data.
WithAtomic commits: readers see the old version or the new one, never a mix.
WithoutSomeone adds a column upstream and downstream reports break silently.
WithSchema is versioned and enforced; evolution is explicit and backward compatible.
WithoutDeleting one customer for a privacy request means rewriting terabytes.
WithRow-level deletes and updates mark rows without rewriting the files.
WithoutA bad load overwrites good data and there is no way back.
WithEvery commit is a version: time travel, audit, rollback.
WithoutQueries list thousands of files and scan most of them.
WithFile statistics let the engine skip files it does not need to open.
WithoutTwo teams write the same folder and corrupt each other's output.
WithOptimistic concurrency detects conflicting writes and rejects one safely.
The cost

These guarantees are not free. Someone must own compaction of small files, expiry of old versions and the catalog itself. A table format without maintenance degrades within weeks.

How to pick

Do not choose a format. Answer three questions and it chooses itself.

1. Which engine writes the table?Its native format wins. Fighting the writer means paying for a translation layer on every commit.
2. Which catalog governs it?The ten-year decision. Sets governance, credentials, and who can add a writer later.
3. Who else must read it without a copy?Picks the interop layer, not the format. One writer per table; everyone else reads a projection.
If your estate looks like thisPick
Fabric or Databricks does the writingDelta. Serve Iceberg readers through UniForm, OneLake virtualization, or managed Iceberg tables.
Snowflake, AWS or Google does the writingIceberg. It is the only open format those platforms write.
Many engines, no dominant platformIceberg plus a vendor-neutral REST catalog (Polaris or equivalent). The one case where Iceberg is chosen on its own merits.
Two platforms both want to write the same tablesNot a format problem. Fix ownership first: one writer per table.

Microsoft Fabric

In Fabric the format is already decided. Spend the decision on interop.

What is fixed

  • Every Fabric engine writes Delta to OneLake: Spark, Warehouse, pipelines, mirroring
  • SQL endpoint and Direct Lake read Delta only
  • Iceberg comes in as a read-only Delta projection: OneLake generates the Delta metadata automatically
  • Iceberg goes out as virtual Iceberg metadata plus a read-only Iceberg REST endpoint on OneLake

Three interop paths

  • Snowflake or any Iceberg reader needs Fabric data: point it at the OneLake table endpoint; no copy
  • Snowflake, Glue or BigQuery writes, Fabric reads: shortcut or mirror the Iceberg table; OneLake virtualizes it to Delta
  • Databricks writes, Fabric reads: mirror the Unity Catalog into Fabric, or store Unity managed tables in OneLake

Guardrail 1

One writer engine per table. Deletion vectors are on by default in Spark Runtime 2.0 and Python notebooks cannot write to those tables.

Guardrail 2

Incoming Iceberg must be V2, under 5000 commits, updated slower than every two minutes, and reachable over the public network.

Guardrail 3

OPTIMIZE and VACUUM need an owner and a schedule, with retention longer than your slowest reader.
