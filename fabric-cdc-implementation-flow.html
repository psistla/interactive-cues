Data Platform Architecture

Change Data Capture in Microsoft Fabric

An implementation flow, not a feature list. Six stages from decision gate to production validation, with the divergence points and the failure modes that appear three months after go-live.

Verification note. Preview status, connector coverage, and replication cadence change on a monthly release cycle. Every item flagged Preview below reflects Microsoft Learn documentation as of August 2026. Re-verify against Learn before attaching any of it to a roadmap with a committed go-live date.

Stage 1: Pick the mechanism

There is no single CDC feature in Fabric. There are three mechanisms operating at two boundaries. Choosing the wrong one is recoverable in week two and expensive in month six.

Boundary 1

External source into OneLake

Mirroring, Copy Job CDC, and Eventstream CDC connectors. This is what most people mean when they ask about CDC in Fabric. It lands changed rows in bronze.

Boundary 2

Table to table inside Fabric

Delta Change Data Feed. This is what most people needed and did not enable, then discovered when silver and gold were still doing full reloads against a near real time bronze.

Three questions, in order

  1. Is the source on the mirroring list?

    Mirroring is the default and everything else needs a reason to beat it. Replication compute is free and does not consume capacity units, and storage is free up to one terabyte per CU purchased. That is a hard economic baseline to argue against, and the output lands as Delta in OneLake so Direct Lake works over it immediately.

    Yes: mirroring, unless Q2 or Q3 overrides No: Copy Job CDC, Eventstream CDC, or open mirroring via partner
  2. Do you need the change events, or just current state?

    Mirroring and Copy Job SCD Type 1 give you a synced replica. They will not tell you what a row looked like before it changed. Audit trails, event driven action, and slowly changing dimension history all require the event itself, not the end state.

    Current state: mirroring or Copy Job SCD1 merge History: Copy Job SCD2, or CDF on top of mirroring Event driven: Eventstream CDC
  3. Where does the change go next?

    Mirroring stops at bronze. Propagating incrementally into silver and gold is a separate problem with a separate mechanism, and skipping it means you built a near real time bronze feeding a nightly full reload. Covered in stage 5.

    Always: plan the CDF layer before you build bronze

Stage 2: End to end flow

Converge, gate, diverge into three lanes, reconverge. The source side work is the critical path and sits before any Fabric configuration, which is the opposite of how these projects are usually planned.

1

Inventory sources and classify change semantics

Per source table: does it have a reliable primary key, does it experience hard deletes, what is the acceptable staleness, and does anyone downstream need the pre-change value. Tables without a primary key cannot be merged and need a different pattern.

Owner: data architect · Output: source register
◆

Decision gate: mechanism per source class

Run the three questions from stage 1. Record the choice and the falsifier per source class, not per table. A per table decision produces an unmaintainable estate.

Owner: data architect · Output: written routing rule
2

Source side enablement and approval

Longest lead item, always. Log reader overhead, transaction log growth, replication slot management, and a change control against a production OLTP system. Start here, in parallel with everything else. Detail in stage 3.

Owner: source DBA · Output: signed change record
3

Network and identity path

Public endpoint, on-premises data gateway, or Eventstream virtual network injection. Decide the authentication method now: workspace identity is not supported for every source, and discovering that during a build sprint costs a week.

Owner: platform and network · Output: connection tested from Fabric
4

Workspace topology and capacity assignment

Mirrored databases are workspace items and follow your promotion path. Do not land replication into a workspace that shares capacity with production interactive reporting until you have measured the read pattern.

Owner: platform · Output: dev, test, prod workspaces on assigned capacity

Divergence: three lanes

Lane A: Mirroring

GA
  1. Create the mirrored database item and authenticate to the source
  2. Select whole database or specific tables
  3. Set retention under Delta table management before first sync
  4. Enable delta change data feed at the same time, not later
  5. Start replication and monitor the replication status page
  6. Validate row counts and delete propagation against source

Lane B: Copy Job CDC

GA
  1. Create Copy job, connect source, confirm the CDC enabled icon on every selected table
  2. Select destination and set update method (Merge or SCD Type 2)
  3. Select incremental copy; no watermark column is required for CDC tables
  4. Decide column mapping explicitly; the schema evolution behaviour differs with and without it
  5. First run performs a full load, subsequent runs are incremental
  6. Schedule and validate

Lane C: Eventstream CDC

GA
  1. Add the CDC source connector from Real-Time hub or an eventstream
  2. Choose schema handling: analytics ready via DeltaFlow, or raw CDC events
  3. Associate an event schema set for schema registry awareness
  4. Route to Eventhouse, Lakehouse, or Activator destinations
  5. Configure virtual network injection if the source is not publicly reachable
  6. Validate event ordering and late arrival handling
5

Reconverge: downstream propagation via CDF

All three lanes land Delta in OneLake. Silver and gold consume changes through Change Data Feed rather than full reloads. Detail in stage 5.

Owner: data engineering · Output: incremental silver load
6

Validation, monitoring, and parallel run

Reconciliation against source, delete propagation test, latency measurement at peak, capacity metrics baseline. Parallel run until reconciliation passes for a full business cycle, then decommission the old feed with a date.

Owner: joint · Output: signed cutover

Stage 3: Source side preparation

The Fabric side of CDC is close to trivial. The project stalls here, in a negotiation with people who own a production transactional system and have no incentive to help you.

! Weakest assumption in the entire plan. That your source DBAs will enable CDC. Confirm source side approval before you scope the Fabric side. A Fabric estimate that assumes log based capture, delivered to a client whose DBAs then refuse it, is an estimate for a project that does not exist.

Per source requirements

SourceMechanismWhat the DBA actually has to agree to
SQL Server / Azure SQL DB / SQL MI Transaction log scan Enabling the capture feature, granting replication permissions, and accepting log reader overhead plus log growth if the reader falls behind. In SQL Server 2025 the engine scans the log at high frequency and publishes per table to the Fabric landing zone.
Oracle LogMiner Supplemental logging enabled, LogMiner available, and a database user with CDC operation privileges. Supported from 12c (12.1) onward including 19c, 21c, and Autonomous Database.
PostgreSQL Logical decoding Logical replication configured and a replication slot. An abandoned or stalled slot retains WAL indefinitely and will fill the source disk. This is the single most likely way a CDC pilot takes down a production database.
Snowflake Streams Grants for CREATE STREAM, SELECT, SHOW TABLES, DESCRIBE. Views and materialized views sync on a twelve hour cadence, not continuously. External, transient, temporary, and dynamic tables are not supported.
SAP Datasphere replication flow or certified partner Replication flow configured with Group Delta set to None and file type Parquet, load type Initial and Delta. Or a certified extractor (Theobald, SNP, ASAPIO, AecorSoft, Simplement) writing to open mirroring.
MongoDB / Cosmos DB Change stream Collection level change stream access. Document model means schema handling decisions move downstream rather than disappearing.

Questions to put to the DBA in writing

  • What is the current transaction log growth rate and retention policy?Log based capture changes both. If the reader stalls, log truncation stops. You need the headroom number before you turn anything on.
  • Is there a read replica or secondary we can capture from?Some connectors support routing to a readable secondary, which removes most of the objection. It typically constrains the isolation mode, so confirm the combination is supported.
  • Which tables experience hard deletes?This determines whether watermark based incremental copy is even viable as a fallback. Soft delete estates have more options.
  • What happens to capture when the source is failed over or patched?Resumption behaviour after failover is the thing to test in dev, not discover in production during a Sunday maintenance window.
  • Who monitors the replication slot or capture job, and against what alert?If the answer is nobody, you have designed an outage with a delay fuse.
× If source side capture is refused, the honest fallback is watermark based incremental copy, and you must tell the client in writing that deletes will not propagate. Reconciliation will drift and the drift will be discovered by a finance user, not by your pipeline. That conversation is far cheaper before build than after.

Stage 4: Fabric side configuration

Three lanes, each with the specific settings that are painful to change after first sync.

Lane A: Mirroring

  • Create the mirrored database, authenticate, and select whole database or specific tables.
  • Set retention before first sync. Mirrored databases created from the portal after mid June 2025 default to one day. Older ones default to seven. Mirroring runs VACUUM automatically to remove files no longer referenced by the Delta log.
  • Enable delta change data feed at creation. Portal: gear icon, Delta table management, enable delta change data feed. CDF is not retroactive, so enabling it in month three loses months one and two.
  • Mirroring creates a SQL analytics endpoint automatically. It is read only. Do not plan writes against it.
  • Mirroring requires a running capacity. Paused or deleted capacity means no replication.

Retrofitting CDF onto an existing mirrored database requires the REST API, since the portal toggle applies going forward:

# 1. Retrieve current definition
POST /v1/workspaces/{workspaceId}/mirroredDatabases/{id}/getDefinition

# 2. Base64 decode mirroring.json, add the property under target.typeProperties
{
  "type": "MountedRelationalDatabase",
  "typeProperties": {
    "defaultSchema": "dbo",
    "format": "Delta",
    "enableDeltaChangeDataFeed": true,
    "retentionInDays": 7
  }
}

# 3. Re-encode and update, then re-read to confirm
POST /v1/workspaces/{workspaceId}/mirroredDatabases/{id}/updateDefinition

Lane B: Copy Job CDC

  • The source picker shows a distinct icon for CDC enabled tables. Confirm it appears on every table you select.
  • Never mix CDC enabled and non-CDC tables in one Copy job. If you do, the job treats all tables as watermark based and deletes silently stop propagating. Split them into separate jobs.
  • Update method: Merge (SCD Type 1) is the default and gives a current state replica. SCD Type 2 Preview adds Valid_From, Valid_To, and Is_Current with soft delete handling, applied consistently across all selected tables.
  • The first run is a full load. Subsequent runs are incremental via CDC.
  • Decide column mapping deliberately. With mapping configured, a deleted or renamed mapped source column fails the run. Without mapping, a deleted column simply stops syncing and the run succeeds. Neither behaviour syncs newly added source columns.
!SCD Type 2 is not supported for Oracle sources, and is not supported if you pre-create the schema in the destination database. Verify before designing a history model around it.

Lane C: Eventstream CDC

  • Add the source from Real-Time hub or directly in an eventstream. Connectors are Debezium based.
  • Schema handling is the load bearing choice. DeltaFlow Preview transforms raw CDC events into analytics ready streams mirroring the source table structure, enriches with change type and timestamps, and manages destination tables and schema evolution. Raw CDC events gives you the unshaped Debezium payload with optional schema registry autodiscovery.
  • Enable event schema association and point it at a schema set so downstream consumers have a contract.
  • If the source is not publicly reachable, use Eventstream connector virtual network injection. This is supported for the SQL, PostgreSQL, MySQL, Oracle, Cosmos DB, and MongoDB CDC connectors among others.
  • For SQL sources, a snapshot select statement override lets you restrict the initial snapshot to a subset of rows. It affects the snapshot only, not the ongoing log read.
iChoosing raw events because DeltaFlow is preview is a defensible call, but it moves schema evolution handling into your own code permanently. Make that trade consciously rather than by default.

Stage 5: Propagate changes downstream

The stage most implementations skip. A fifteen second bronze feeding a nightly full reload of silver is not a CDC architecture; it is an expensive landing zone.

Enable Change Data Feed

CDF is a standard Delta table property. Enable it at creation, or alter an existing table. It captures changes only from the moment it is enabled and does not backfill.

-- At creation
CREATE TABLE sales.orders (
  order_id BIGINT, customer_id BIGINT,
  order_status STRING, order_total DECIMAL(18,2)
) USING DELTA
TBLPROPERTIES (delta.enableChangeDataFeed = true);

-- On an existing table
ALTER TABLE bronze.orders
  SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

Read the changes

Batch, by version or timestamp

-- Bounded version range
SELECT * FROM table_changes('sales.orders', 120, 125);

-- Timestamp range
SELECT * FROM table_changes(
  'sales.orders',
  TIMESTAMP '2026-05-01T00:00:00Z',
  TIMESTAMP '2026-05-01T23:59:59Z');

Structured Streaming

changes = (spark.readStream.format("delta")
    .option("readChangeFeed", "true")
    .table("sales.orders"))

(changes.writeStream.format("delta")
    .outputMode("append")
    .option("checkpointLocation",
            "Files/checkpoints/orders_changes")
    .toTable("sales.orders_changes"))

First stream read processes the full initial snapshot as insert events, then picks up only new changes. You do not seed the target separately.

ColumnMeaningWhy it matters downstream

Stage 6: Failure modes and validation gates

Four of these belong in the assumptions block of any deliverable. Each fails silently, which is why they surface in month three rather than week one.

Silent

Retention shorter than consumer cadence

CDF captures nothing before it is enabled, and VACUUM deletes _change_data files outside the retention window. Portal created mirrored databases default to one day retention. A one day retention plus a weekly downstream job equals data loss with no error raised.

Gate: retention window must exceed the longest downstream consumer interval by a full recovery cycle, not by a margin.

Silent

Copy Job degrades to watermark mode

Selecting CDC enabled and non-CDC tables in the same Copy job causes all tables to be treated as watermark based. Deletes stop propagating and no error is raised.

Gate: every table in a CDC Copy job shows the CDC enabled icon. Separate jobs otherwise.

By design

Net change only

Copy Job CDC captures net change, not full change history. A row changed five times between runs yields the final state, not five events. Full change capture is stated as coming later.

Gate: if audit or compliance requires every intermediate state, route through Eventstream or CDF, not Copy Job.

Operational

Paused capacity halts replication

Mirroring requires a running capacity. Paused or deleted capacity means nothing replicates, although the background compute does not consume CU while it runs.

Gate: test resumption behaviour after an extended pause in dev before any non-production capacity pause schedule goes live.

Secondary failure modes

  • Small file accumulation under _change_data. CDF writes extra files as part of change history, not the active snapshot. High churn tables need a maintenance schedule, and that schedule interacts with retention.
  • Custom capture instances are not supported in Copy Job CDC; only the default capture instance. Estates that already run named capture instances for other consumers need a plan.
  • CDF status on Fabric Lakehouse tables cannot be autodetected by Copy Job. You must know and track it yourself.
  • Snowflake views and materialized views sync every twelve hours, not continuously. A dashboard built on a mirrored view is a twice daily dashboard regardless of what the mirroring page says about latency.
  • Shortcut based patterns move the failure domain, they do not remove it. An outage in the source store is an outage in your gold layer.

Validation gates before cutover

  • Row count reconciliation passes across a full business cycleNot a single point in time check. Month end and period close are where drift appears.
  • Delete propagation verified explicitlyDelete a test row at source, confirm it disappears in bronze and is handled correctly in silver. This is the single test that separates real CDC from watermark copy.
  • Latency measured at the peak concurrency hour, not the averageReplication latency depends on source region, change volume and frequency, network bandwidth, and gateway compute. Measure it where the constraint actually binds.
  • Schema change rehearsed, not assumedAdd a column, drop a column, change a type at source in dev. Confirm the observed behaviour matches what you documented for the mechanism you chose.
  • Capacity metrics baseline captured before go-liveAny sizing produced before instrumentation is an estimate. Label it as one, set a review date, and revisit after two weeks of production load.
  • Preview components flagged with a stated consequenceFor each preview item on the critical path, write down what happens to the roadmap if it stays preview for another year. If that answer is unacceptable, it does not belong on the critical path.
  • Decommission date for the replaced feed is written and ownedIf the old extract keeps running, the business case that justified this work never closes.
