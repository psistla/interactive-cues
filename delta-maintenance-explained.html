01

A table is files plus a diary

Your table isn't one thing. It's a folder of data files, plus a diary that records every change ever made. Every maintenance question is a question about one or the other.

Your table · tap the diary to see which files each change touched

The diary

The diary is the transaction log: an ordered record of commits, each listing files added and files removed. Readers use the log, not the folder listing, to know which files are "the table" right now.

transaction log_delta_logcommit

Commits are JSON entries; periodic checkpoints summarize them so readers don't replay the whole history. Files are immutable: a change never edits a file, it writes new ones and logs the swap. That immutability is what makes everything else on this page possible.

02

Tables get messy by default

Every write adds files. Frequent small writes add lots of tiny files, and reading many tiny files is slow. Nothing is broken; results stay correct. The table just quietly decays. Try it.

Decay lab · watch the health strip above
tiny files 0 query reads 0 files

This is the small file problem. Each file read carries fixed overhead (open, footer, metadata), so 800 files of 1 MB cost far more than 8 files of 100 MB. Streaming appends, trickle loads, and per-key writes are the usual culprits.

small file problemfile overhead

Healthy target: roughly 128 MB–1 GB per file depending on table size. Some engines reduce decay at write time (pre-write bin packing, automatic compaction), trading write cost for read health. Decay rate is a design property of your ingestion pattern, not bad luck.

03

Compaction: merge small into large

The fix is simple: combine many tiny files into a few big ones. Same rows, fewer files, faster reads. One command does it.

Repair lab · needs tiny files from step 02
note: disk usage didn't drop — old copies remain until cleanup (04)

This is bin-compaction, the OPTIMIZE command. It writes new large files, then logs a commit that swaps them in. The old small files stay on disk as history — which is why compaction improves speed but not storage.

OPTIMIZEbin-compaction

Compaction can be scoped (only recent partitions or files needing work) to avoid rewriting the whole table. On very large tables, unscoped compaction is itself a cost problem; modern engines select only unhealthy files. Run it after heavy ingestion, not after every write.

04

Cleanup reclaims space

Old copies pile up on disk so you can rewind (next card). Cleanup deletes copies older than a retention window you choose. Space back; oldest history gone.

Cleanup lab
7 days

This is VACUUM with a retention period. It removes files no longer referenced by the current table and older than retention. Common default: 7 days. Platforms often guard against shorter windows, because deleting files a running query still needs corrupts reads.

VACUUMretention

Retention below the guardrail usually requires explicitly disabling a safety check — a deliberate friction. Anything that pins an old version (a long-running reader, a downstream cache, a snapshot-based consumer) must be accounted for before shrinking retention. Cleanup is the one maintenance command that destroys.

05

Rewind and cleanup are in tension

Because old copies stay on disk, you can rewind the table to any past version — until cleanup deletes the files that version needs. How far you can go back is exactly what you haven't thrown away.

Time travel lab · try rewinding, then clean up in 04 and try again

This is time travel: query a version or timestamp, or restore the table to it. It's your undo, audit trail, and reproducibility tool. Retention is therefore a contract: the cleanup schedule defines the recovery window.

time travelVERSION AS OFRESTORE

The diary entry may still exist after cleanup, but the files it points to don't — rewinding then fails. Decide retention from recovery needs ("we must be able to undo a bad load within N days"), write it down, and treat any change to it as a policy change, not a tuning knob.

06

Layout: keep similar rows together

If rows with similar values sit in the same files, a query can skip whole files that can't contain its answer. Skipped files are free. Compare a messy layout with a sorted one.

Each file stores min/max statistics per column; the engine skips files whose range excludes the filter. Layout techniques — clustering, partitioning, multi-column ordering — exist to make those ranges narrow and non-overlapping on the columns you filter by most.

data skippingclusteringpartitioningZ-order

Choose 1–4 real filter columns; more dilutes the benefit. Directory-style partitioning suits huge tables with low-cardinality lifecycle keys but creates tiny-file explosions on high-cardinality ones; modern clustering avoids that and can be changed later. Small tables often need no layout strategy at all — measure before adding one.

07

Deletes are bookmarks first

Files can't be edited, so deleting a row doesn't rewrite the file. The row gets a bookmark that says "ignore me." Fast — but bookmarks accumulate. Eventually you tidy up for real.

Delete lab · tap rows in this file to delete them
✕ = deleted-by-bookmark. Readers filter these out on every query.

Bookmarks are deletion vectors: sidecar files marking dead rows, applied at read time ("merge-on-read"). They make UPDATE, DELETE, and MERGE much faster. The tidy-up rewrite is a purge; compaction typically purges heavily bookmarked files automatically.

deletion vectorsmerge-on-readPURGE

One consequence matters legally: bookmarked data still exists in the file. Compliance deletes (right-to-be-forgotten) require an explicit purge rewrite followed by cleanup of the old files — a bookmark alone does not remove the bytes.

08

Measure, don't guess

Two questions diagnose almost everything: what does the table look like right now, and what has been happening to it? Ask them before and after every intervention. Ask them about the table you built on this page.

Diagnosis lab

The two questions have names: DESCRIBE DETAIL (file count, sizes, current state) and DESCRIBE HISTORY (the diary itself: operations, versions, timestamps). A rough smell test: hundreds of files averaging well under ~32 MB is a compaction candidate.

DESCRIBE DETAILDESCRIBE HISTORY

Trend beats snapshot: file count growing linearly with time means ingestion is producing decay faster than maintenance removes it — fix the write pattern, not just the symptom. Never assert an effect you didn't measure; before/after numbers are what make maintenance a discipline instead of a ritual.

09

Hygiene, not firefighting

Maintenance is scheduled, like backups — not a reaction to a slow dashboard. Pick a cadence, write it down, automate it. Assemble a starter policy:

Your runbook appears here.

A reasonable default on any platform: compact after major ingestion or when small files accumulate; clean up weekly with retention set from your recovery contract; revisit layout when query filters change. Automate via whatever scheduler your platform gives you — notebook jobs, pipelines, or APIs.

cadenceautomation

Cadence has consumers. Compaction invalidates downstream caches briefly (cold-read penalty, then faster steady state); cleanup interacts with anything pinned to an old version. Schedule maintenance in the quiet windows of the systems that read the table, and note the dependency in the runbook itself.

Scope note. Everything above is platform-agnostic Delta Lake behavior; command names follow the open-source project, and vendors add their own write-time optimizations and scheduling tools on top.
