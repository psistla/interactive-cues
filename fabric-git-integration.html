Deployment gotchas that will bite this design
Direct Lake semantic models do not autobindDeploy a lakehouse and its Direct Lake model together and the model in the target stage still points at the lakehouse in the source stage. Every other semantic model type autobinds to the paired item. Fix with a datasource rule in the target stage. Until you do, test reads dev data and looks entirely healthy doing it.
  • Lakehouse deploy creates an empty lakehouse of the same name in the target and remaps notebooks and Spark job definitions to it. With a dependency mapping configured, the empty lakehouse is still created but references point to the mapped one.
  • Deploy overwrites shortcut state in the target lakehouse. All shortcuts are created, updated, or deleted to match source. Use Review changes first.
  • RLS role assignments are not copied. Neither are refresh schedules, data source credentials, query caching settings, endorsement settings, permissions, or workspace settings. Each is configured per stage, by hand.
  • Gateway mapping is not automatic after the initial deployment. Map it in the target item's settings and verify a refresh. Later deployments leave it alone.
  • Sensitivity labels copy only in narrow cases: a new item, an existing item into an empty stage, or a protected source label over an unprotected target (which prompts for consent).
  • Ownership moves on first deploy. The deploying user becomes owner of cloned semantic models and dataflows. Paginated report ownership transfers on every deploy.
  • Hard caps: 300 items per single deployment; circular or self dependencies fail; PBIR reports unsupported; post-deployment .pbix download unsupported.

The commit-before-deploy control

Git and deployment pipelines never talk to each other. The pipeline copies the live dev workspace; it does not read your branch. Nothing prevents deploying an uncommitted change, and when that happens prod holds a state that exists in no commit.

  • Before any deploy, open the dev Source control panel.
  • If the uncommitted count is not zero, commit or undo. Do not deploy past it.
  • Commit message names the release, so the commit is findable from the deployment note.
  • Deployment note names the commit message, so the deployment is findable from the branch.

That reciprocal naming is the entire trace this model gives you. If an auditor asks which commit is running in prod, the honest answer is that you infer it from two matching free-text strings. If that is unacceptable, the promotion decision is what needs revisiting, not the procedure.

Hard limits

Git integration, both providers

  • 1,000 items maximum per workspace. A branch holding more fails to sync.
  • Full file path maximum 250 characters. Branch name maximum 244 characters.
  • Maximum file size 25 MB. Folder structure preserved to 10 levels deep.
  • One branch and one folder per workspace at a time. One sync direction at a time.
  • Submodules not supported. Sovereign clouds not supported.
  • Sensitivity labels not supported in sync; exporting labeled items may be disabled pending an admin switch.
  • Display names over 256 characters, ending in a period or space, or containing " / : < > \ * ? | cause the Git folder to be renamed to a GUID plus type.
  • An item recreated by both Git and the recycle bin produces two identities and can stop Git integration working. Delete the Git-recreated copy.

Deployment pipelines

  • 300 items maximum per single deployment.
  • Stage count and names are permanent after creation.
  • Circular or self dependencies fail the deployment.
  • PBIR reports not supported. Post-deployment .pbix download not supported.
  • Real-time connectivity semantic models cannot be deployed.
  • Dataflow Gen2 (CI/CD) as a semantic model datasource is not supported for deployment.
Open questions, ranked by how much the answer changes the design
  • Which provider, and is it cloud-hosted? Self-hosted on either side invalidates the approach. Questions 1 and 2 resolve it.
  • On Azure DevOps, is the organization in the Fabric tenant? If not, service principal creation needs one CLI or PowerShell command, which is the only non-clickable step in this runbook.
  • Are dev, test, and prod inventories aligned by name, type, and folder? If not, first assignment produces pairing failures or silent duplicates.
  • Are any semantic models Direct Lake? If yes, datasource rules are mandatory, not optional.
  • Do bronze shortcuts point at the same storage in all three environments? If not, you need Variable Library (preview) or a manual post-deploy fix.
